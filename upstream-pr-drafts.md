## PR 1: check_syntax: dynamic attribute access on a generic object reference

Compare: https://github.com/abaplint/abaplint/compare/main...oblomov-dev:fork-abaplint:fix-dynamic-attribute-generic-object?expand=1

### Problem
Dynamic attribute access `oref->(name)` on a variable typed `REF TO object` reports
`Not an object reference, target` (write position) or `Not an object reference, field chain` (read position). The code activates on the system.

```abap
DATA mo_app TYPE REF TO object.
mo_app->('MV_FLAG') = abap_true.
IF mo_app->('ZIF_DEMO~MV_VIEW') = abap_true.
ENDIF.
```

ABAP keyword documentation, [Object Component Selector, Dynamic Component](https://help.sap.com/doc/abapdocu_latest_index_htm/latest/en-US/ABENOBJECT_COMPONENT_SELECTOR.html):
"A component of an object can be specified dynamically with the following syntax: `... { dref->(comp_name) } | { cref->(attr_name) } | { iref->(attr_name) } ...` The syntax and meaning is the same as for dynamic components and dynamic access in the statement ASSIGN and the result of the expressions behave like an accordingly assigned field symbol of type ANY."

### Change
`Target` and `FieldChain`: after `->`, a `GenericObjectReferenceType` followed by `(` is a dynamic attribute, the result type is void. A static attribute on `REF TO object` (`mo_app->mv_flag`) is still an error.

### Tests
`test/abap/syntax/syntax.ts`, describe "dynamic attribute of a generic object reference": write target, comparison, interface attribute name, name in a variable (4 fail before the change), and the static attribute error case.

## PR 2: check_syntax: INSERT INTO TABLE dref->* and LINES OF dref->* with a generic data reference

Compare: https://github.com/abaplint/abaplint/compare/main...oblomov-dev:fork-abaplint:fix-generic-dereference-lines-of?expand=1

### Problem
```abap
DATA mr_tab TYPE REF TO data.
DATA lr_source TYPE REF TO data.
DATA lt_copy TYPE string_table.
INSERT LINES OF lt_copy INTO TABLE mr_tab->*.   " INSERT target must be a table
APPEND LINES OF lr_source->* TO lt_copy.          " LINES OF must be a table type
```
Both activate on S/4HANA.

ABAP keyword documentation, [Dereferencing Operator](https://help.sap.com/doc/abapdocu_latest_index_htm/latest/en-US/ABENDEREFERENCING_OPERATOR.html):
"For data reference variables with the generic static type data, it can be specified at any operand position except for: Replacement parameters behind DEFAULT for methods, functions or events. Components of internal tables. Operand positions where an index table is expected."

[INSERT, line_spec](https://help.sap.com/doc/abapdocu_latest_index_htm/latest/en-US/ABAPINSERT_ITAB_LINESPEC.html) and [APPEND, line_spec](https://help.sap.com/doc/abapdocu_latest_index_htm/latest/en-US/ABAPAPPEND_LINESPEC.html): "LINES OF jtab ... jtab is a functional operand position."

### Change
- `INSERT ... INTO TABLE dref->*`: a dereferenced generic data reference is accepted as target (key access, any table). `INSERT ... INTO dref->* INDEX n` expects an index table and is still an error.
- `APPEND LINES OF dref->*`: accepted without `FROM`/`TO` index (`FROM idx1 TO idx2` work like LOOP on an index table, so that is still an error).
- A generic operand that is not dereferenced (`IMPORTING data TYPE data`) is still not a table, as in the existing test "INSERT, not an internal table, generics".

### Tests
`test/abap/syntax/syntax.ts`, describe "LINES OF and INSERT with a generically typed dref->*": 3 ok cases fail before the change; error cases for INDEX, FROM/TO and a non-dereferenced generic parameter.

## PR 3: unsecure_fae: no issue when the driver table is checked for initial

Compare: https://github.com/abaplint/abaplint/compare/main...oblomov-dev:fork-abaplint:fix-unsecure-fae-guard?expand=1

Closes #2384

### Problem
`unsecure_fae` reports every FOR ALL ENTRIES, the check for an initial driver table was a todo:
```abap
IF it IS NOT INITIAL.
  SELECT * FROM t000 FOR ALL ENTRIES IN @it WHERE mandt = @it-table_line INTO TABLE @lt_t000.
ENDIF.
```

### Change
The driver table counts as checked, and no issue is reported, if
- the SELECT is in the IF or ELSEIF branch of `itab IS NOT INITIAL`, `NOT itab IS INITIAL` or `lines( itab ) > 0` (also `GT 0`, `<> 0`, `>= 1`), alone or AND-combined, also in a parenthesized AND sub-condition;
- or `IF itab IS INITIAL. RETURN. ENDIF.` (condition alone or OR-combined, body only RETURN, no ELSE) or `CHECK itab IS NOT INITIAL.` (the variant from #2384) precedes the SELECT in the same method, form or function module, at the same or an outer block level, not inside a loop;

and the table is not written (Target / FSTarget) between the check and the SELECT, or in a loop around the SELECT within the checked region. For tables that are not local variables or parameters (attributes, `me->x`, field symbols), a method/function/form call in between also invalidates the check. Kept conservative on purpose: OR in the guard, ELSE branch, NOT ( ... ), dynamic driver names are still reported. The rule documentation describes the scope and now has a bad/good example.

### Tests
`test/rules/unsecure_fae.ts`: 14 checked cases in a method plus the program-level shape of #2384 (these 15 fail before the change), and 15 unchecked cases that must still report.

## PR 4: suspicious_loop: a helper declared inline in the loop body changes the source

Compare: https://github.com/abaplint/abaplint/compare/main...oblomov-dev:fork-abaplint:fix-suspicious-loop-inline-declaration?expand=1

### Problem
```abap
DATA(lv_total) = lines( lt_t000 ).
DATA(lv_from) = 1.
WHILE lv_from <= lv_total.
  DATA(lv_to) = lv_from + 10 - 1.
  lv_from = lv_to + 1.
ENDWHILE.
```
Reported as "WHILE condition does not change after the first iteration, the loop body sets lv_from to the same value in every iteration". `lv_to` is set from `lv_from` in every iteration, but its inline declaration is not one of `Variable.writes()`, so the source `lv_to + 1` looked unchanged.

### Change
`sameValueWrite` treats a local as changed in the loop if it is written in the body or declared inline in the body.

### Tests
`test/rules/suspicious_loop.ts`: two cases (the example above, and `DATA(lv_next) = lv_i + 1. lv_i = lv_next.`), both fail before the change.
